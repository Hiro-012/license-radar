license-radar reads setup.cfg's install_requires — but not when it points at a file

By HiroCheck · Published 2026-09-26

setuptools supports declaring a package's dependencies in setup.cfg two ways: inline, one requirement per line, or by pointing at another file — install_requires = file: requirements/base.txt — so the same requirements file can be shared between pip install -r and packaging metadata. It's a common layout in projects that keep a requirements/ directory split into base.txt, dev.txt, prod.txt, etc. license-radar's README says it reads setup.cfg's install_requires. It does — right up until the value is a file: reference, at which point it silently drops the line instead of following it.

The function, as implemented

# license_radar/parsers.py
def _split_cfg_list(value: str) -> list[str]:
    """Split a setup.cfg list-valued option into individual requirement lines.

    setuptools stores install_requires / extras_require entries one per
    line. A leading file: directive (setuptools reads the list from another
    file) is not a requirement and is skipped.
    """
    lines = []
    for raw in value.splitlines():
        line = raw.strip()
        if not line or line.startswith("file:"):
            continue
        lines.append(line)
    return lines

The docstring is accurate about what the code does — it just means the dependency list setuptools would actually install is never read at all. There is no code path anywhere in parse_setup_cfg() that opens the file named after file:, unlike the tool's own handling of pip's -r other.txt include syntax in requirements.txt, which it does follow.

Not fixed by renaming the file, either

Even setting the file: indirection aside, the referenced file would still need to be independently discoverable for license-radar to have any chance of scanning it on its own, and the filenames this setup.cfg pattern is normally used with — base.txt, prod.txt, dev.txt — don't start with requirements, so _matches_manifest()'s requirements*.txt rule (the same prefix-only rule covered by this blog's earlier dev-requirements.txt article) wouldn't pick them up even if someone thought to check. That's a compounding, not incidental, detail: this file: gap can't be worked around by simply relying on independent discovery of the target file, because the file it names is exactly the kind of name that discovery already misses.

Reproduced against the unmodified CLI

$ cat setup.cfg
[metadata]
name = myproject
version = 1.0.0

[options]
packages = find:
install_requires = file: requirements/base.txt

$ cat requirements/base.txt
requests==2.31.0
pyqt5==5.15.9

$ python3 -m license_radar.cli scan .
No dependencies found.

OK — no policy violations
$ echo $?
0

$ python3 -m license_radar.cli scan . --json
{
  "findings": [],
  "violation": false
}
$ echo $?
0

pyqt5 is in license-radar's own curated database as GPL-3.0-only — a strong-copyleft license the default policy is specifically built to catch. The scan reports the same clean "OK" it would give an empty project.

Control: the identical dependency list, discoverable

To confirm the miss is specifically about the file: indirection and the discovery pattern — not some other difference — the same two lines, saved directly as a top-level requirements.txt instead of behind setup.cfg's file: reference, scan exactly as expected:

$ cat requirements.txt
requests==2.31.0
pyqt5==5.15.9

$ python3 -m license_radar.cli scan .
[pypi] requests: Apache-2.0 (permissive)
[pypi] pyqt5: GPL-3.0-only (strong-copyleft) !!

VIOLATIONS FOUND
$ echo $?
1

Same package, same declared version, same policy — the only variable is whether license-radar's manifest-discovery and setup.cfg-parsing code path ever sees it.

Why this is a different gap from the earlier "no recognized manifest" article

An earlier article on this blog (license-radar-no-recognized-manifest-still-reports-ok.html) covers a project with no manifest license-radar recognizes at all — there is nothing for discover_manifests() to find, by design of that example. Here, setup.cfg itself is a manifest the tool fully recognizes and does parse; it's one specific, common way of writing install_requires inside that already-supported file that silently produces zero dependencies instead of an error or a partial result.

How common this layout is

Splitting requirements into a requirements/ directory (base.txt plus environment-specific overlays) predates and coexists with the newer pyproject.toml convention, and setup.cfg's file: directive exists specifically to let a setup.cfg-based package point at that same shared file rather than duplicate it inline. Any project using this combination — common in the years setup.cfg was setuptools' recommended declarative format — has its entire dependency list invisible to a license-radar scan, with no warning that anything was skipped.

A project using this setup.cfg layout can work around the gap today by also keeping a directly-discoverable requirements*.txt at the project root (even a thin one using pip's -r include, which license-radar does follow) until the file: directive itself is supported.

pip install license-radar
license-radar scan .
