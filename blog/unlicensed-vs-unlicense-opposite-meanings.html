"Unlicense" and "UNLICENSED" look like the same word. license-radar treats them as opposites

By HiroCheck · Published 2026-08-29

Two strings, one capitalization change apart: Unlicense and UNLICENSED. They read like the same word typed two different ways. They are not the same license — they are close to opposite answers to the question "can I use this code."

Unlicense: a real, permissive SPDX license

Unlicense is an SPDX-registered license identifier (added to the SPDX License List in 2020), OSI-approved and FSF-approved, with no copyleft requirement. Its own text opens with the plainest possible grant:

This is free and unencumbered software released into the public domain.

Anyone is free to copy, modify, publish, use, compile, sell, or
distribute this software, either in source code form or as a compiled
binary, for any purpose, commercial or non-commercial, and by any means.

A package declaring "license": "Unlicense" is, as close as software licensing gets, saying "take it, no strings attached."

UNLICENSED: npm's marker for the opposite

UNLICENSED is not an SPDX identifier at all — it's npm's own documented convention for the package.json license field, meant for a package the author does not want anyone else to use. It shows up on real, public npm packages, not just private ones — the registry itself reports it as the license string, no interpretation needed:

curl -s https://registry.npmjs.org/unlicensed/latest | python3 -c \
  "import json,sys; d=json.load(sys.stdin); print(d['name'], d['license'])"
> unlicensed UNLICENSED

Whatever the author's actual intent, the string npm's own convention assigns to it means "you do not wish to grant others the right to use a private or unpublished package under any terms" — the closest thing to a license field can get to "no license granted."

What license-radar actually does with each string

Checked directly against the shipped classifier:

>>> from license_radar import classify
>>> classify.classify_license("Unlicense")
'permissive'
>>> classify.classify_license("UNLICENSED")
'unknown'
>>> classify.classify_license("unlicense")   # lowercase
'unknown'
>>> classify.classify_license("unlicensed")  # lowercase, no SPDX form at all
'unknown'

Only the exact SPDX-cased string Unlicense resolves to permissive. Everything else that merely looks like it — npm's UNLICENSED, a lowercased unlicense, or the plain English word unlicensed — falls through to unknown, license-radar's catch-all for "don't guess, flag it for a human." That's the conservative direction to fail in: a package that's actually public domain but gets flagged unknown costs someone a few seconds of review; a proprietary package that gets waved through as permissive doesn't.

This isn't a hypothetical mix-up

The two strings are close enough that even a widely used toolchain's own documentation has recommended the wrong one. Solidity's compiler docs tell authors to use UNLICENSED as the SPDX license identifier comment for closed-source contracts — but as a 2025 issue against the Solidity repository points out, UNLICENSED isn't a valid SPDX identifier at all, and the only valid identifier close enough to autocomplete or copy-paste into its place — Unlicense — means the exact opposite of what the docs intend. If a compiler's own documentation can point developers at the wrong one of these two strings, a person hand-editing a package.json license field, or a reviewer skimming a license report, can just as easily do the same.

What to actually check

If license-radar (or any scanner) reports a package's license as unknown and the raw string looks like some form of "unlicense," don't normalize it away — read which exact string is present. Unlicense (capital U, no trailing marks) is a real permissive grant. Anything else that merely resembles it — UNLICENSED, unlicensed, a lowercase unlicense, or a blank field — means license-radar has no confident answer, which for this pair of strings is exactly the outcome you want: getting it wrong here doesn't fail safe in only one direction.
