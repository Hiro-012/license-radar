license-radar scans Python and npm manifests. A Go or Conda-only repo gets "OK — no policy violations" too

By HiroCheck · Published 2026-09-18

license-radar's README is upfront about what it scans: requirements.txt, pyproject.toml, setup.py, setup.cfg, Pipfile, and package.json. That is Python and npm only — by design, not an oversight. What isn't documented anywhere is what happens when a scan target has none of those files: a Go service (go.mod), a Rust crate (Cargo.toml), or a Conda-managed ML project (environment.yml) all produce the exact same terminal output and exit code as a project that was fully scanned and found clean.

The matching rule, as implemented

# license_radar/parsers.py
def _matches_manifest(name: str) -> tuple[str, object] | None:
    if name == "pyproject.toml":
        return "pypi", parse_pyproject_toml
    if name == "package.json":
        return "npm", parse_package_json
    if name == "setup.cfg":
        return "pypi", parse_setup_cfg
    if name == "setup.py":
        return "pypi", parse_setup_py
    if name == "Pipfile":
        return "pypi", parse_pipfile
    if name.startswith("requirements") and name.endswith(".txt"):
        return "pypi", parse_requirements_txt
    return None

Six exact patterns, all Python or npm. A directory walk that finds none of them returns an empty manifest list — there is no separate "nothing to scan here" signal from that point on. It flows into the same empty-findings path as a directory whose one requirements.txt happened to list only permissively-licensed packages.

Reproduced against the unmodified CLI

A minimal Go module, with nothing else in the directory:

$ cat go.mod
module example.com/foo

go 1.21

require github.com/gpl-licensed/somepkg v1.0.0

$ license-radar scan .
No dependencies found.

OK — no policy violations
$ echo $?
0

The same for a Conda-managed ML project declaring its dependencies in environment.yml instead of a pyproject.toml or requirements.txt — common in data-science and model-training repos that need GPU/CUDA packages a pure-pip install can't provide:

$ cat environment.yml
name: myenv
dependencies:
  - python=3.11
  - some-gpl-package

$ license-radar scan .
No dependencies found.

OK — no policy violations
$ echo $?
0

Both commands were run against this session's unmodified checkout, no code changed. The --json output carries the same ambiguity in machine-readable form — a CI step parsing this has no field to distinguish "scanned, zero violations" from "scanned nothing":

$ license-radar scan . --json
{
  "findings": [],
  "violation": false
}

Why "OK" and "nothing was scanned" look identical on purpose

This isn't a parsing bug in any of the six recognized formats — every existing article on this blog about license-radar's manifest discovery (the dev-requirements.txt naming gap, for instance) is about a file that should have been read and wasn't. This is different: the tool is working exactly as documented, on a project type it never claimed to support. The problem is narrower and easy to miss for exactly that reason — run_scan() in license_radar/cli.py has one branch for "no findings," and it's the same branch whether that's because zero manifests exist or because every manifest that does exist declares only permissive licenses:

# license_radar/cli.py
    if args.json:
        print(json.dumps({"findings": rows, "violation": has_violation}, indent=2))
    else:
        if not rows:
            print("No dependencies found.")
        for row in rows:
            ...
        print()
        print("VIOLATIONS FOUND" if has_violation else "OK — no policy violations")

    return EXIT_VIOLATION if has_violation else EXIT_OK

rows being empty because discover_manifests() found nothing, versus rows being empty because every found manifest classified as permissive, take the same path to the same "OK — no policy violations" line and the same exit code 0. The --online flag changes nothing here either — it only affects lookups for packages already found in a manifest; with zero manifests found there is nothing for it to query.

Where this actually bites

The pre-commit hook config in license-radar's own README scopes itself correctly — it only runs when a commit touches one of the six recognized filenames, so it never has this problem. The gap shows up one level up, in a generic CI job that runs license-radar scan . across an entire repository and treats a non-zero exit code as the only signal that matters (a pattern this project's own gpl-trove-classifier-text-reads-as-unknown.html piece already showed is common for compliance gates). That pattern is exactly where "OK" and "nothing was scanned" needing to be distinguishable matters most: a polyglot monorepo where one service is Python (correctly scanned) sitting next to a Go or Rust service (silently zero-scanned) will show a single green license-radar scan . step covering "this repo," when it only ever covered the Python/npm slice of it. A team that adds the Go service after wiring up the CI step gets no signal that its coverage just changed.

Verification

$ python3 -m pytest tests -q
121 passed

$ python3 scripts/measure_accuracy.py
  packages (ground truth): 305  (scanned end-to-end: 305)
  risky packages       : 13  flagged: 13
  recall               : 100.00%
  false-positive rate  : 0.00%

No code was changed this session — both commands were run against the existing, unmodified checkout, and the 121/121 and 100%/0% figures match the numbers already published in the README's "Detection accuracy" section (this finding doesn't touch classification, so it doesn't move them). The two reproductions above (go.mod, environment.yml) were run directly against license_radar.cli.main in temporary directories created and deleted within this session; neither is a real published package, so no external license claim is being made about either — the point is the CLI's output, not any specific Go or Conda package's actual license.

A CI job that wants an honest signal today can check rows (or the JSON findings array) length independently of violation/exit code, or run license-radar scan . --json and compare the manifest count it expects for that repo against what came back — nothing in the CLI currently does that comparison for you.

pip install license-radar
license-radar scan .
