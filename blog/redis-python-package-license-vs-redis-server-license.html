license-radar says "redis" is MIT. The Redis server hasn't been under one license since 2024

By HiroCheck · Published 2026-08-21

Run license-radar scan on a project that lists redis in requirements.txt (or ioredis in package.json), and it reports MIT, permissive, no violation. That answer is correct — and also easy to misread as saying something it doesn't say.

What the scanner is actually looking at

redis on PyPI and ioredis on npm are client libraries — the code your application imports to talk to a Redis server over its wire protocol. Checked directly against the live registries:

curl -s https://pypi.org/pypi/redis/json | grep -i "License ::"
> License :: OSI Approved :: MIT License

curl -s https://registry.npmjs.org/ioredis/latest | grep '"license"'
> "license": "MIT"

Both are MIT, and that's the license of the client code that ships in your dependency tree. license-radar's offline database has fixed entries for both (redis and ioredis → MIT), which resolve to the permissive tier — verified directly against the shipped database:

>>> from license_radar import license_db, classify
>>> license_db.PYPI_LICENSES["redis"]
'MIT'
>>> classify.classify_license("MIT")
'permissive'

What it isn't looking at

The Redis server — the actual database binary your app connects to — is a completely separate piece of software with its own, much more turbulent license history:

Redis versionLicense
≤ 7.2BSD-3-Clause (permissive)
7.4 (March 2024)Dual SSPLv1 / RSALv2 — source-available, not OSI-approved, not permissive
8.0+ (May 2025)Tri-licensed: RSALv2, SSPLv1, or AGPLv3 (licensee's choice) — AGPLv3 is copyleft, the other two aren't OSI open source at all

In March 2024, Redis Ltd. moved the server off BSD to the Server Side Public License and its own Redis Source Available License, a change significant enough that AWS and Google Cloud responded by forking the last BSD release into Valkey. After community pushback and original author Salvatore Sanfilippo ("antirez") rejoining the company, Redis 8.0 added AGPLv3 as a third option in May 2025 — a partial reversal, not a return to the original permissive terms.

None of that history touches the redis/ioredis client packages. They were MIT before March 2024 and they're MIT now. A scanner that reads requirements.txt or package.json has no way to know — and no reason to know, since it isn't its job — what license governs the separate server binary your app happens to talk to at runtime.

Why this particular gap matters more than usual

Most "is this dependency safe" review workflows start and end with the dependency manifest, because for library code that's usually the whole story: if you pip install it, you're using its code under its license, full stop. Redis breaks that assumption in a way a lot of other infrastructure software does too (Elasticsearch/OpenSearch and MongoDB have similar client-vs-server splits) — the manifest only ever shows the half of the picture that lives in your dependency tree. The half that's a separately-licensed binary you deploy, self-host, or consume as a managed service isn't a "dependency" in the sense any manifest scanner — license-radar included — is built to see.

What to actually check

If a project uses Redis as infrastructure (not just imports a client), the license question that matters is: which Redis license applies to the server version actually deployed, and does that license's terms (SSPL's service-provider clause, RSALv2's usage restrictions, or AGPLv3's copyleft triggers) matter for how the product is distributed or offered as a service. That's a deployment-and-distribution question, not a dependency-manifest question — check it against Redis's own licensing page directly rather than assuming a MIT dependency answers it.

license-radar will correctly keep reporting the client library as MIT/permissive either way — that's an accurate answer to the question it's actually built to answer (what license governs the code in this dependency tree), not to the adjacent one (what license governs the infrastructure this code talks to).

pip install license-radar
license-radar scan .
