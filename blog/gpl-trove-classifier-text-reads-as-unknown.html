PyPI's own GPL classifier text says "GNU General Public License" in plain words — license-radar reads it as unknown

By HiroCheck · Published 2026-09-14

mysql-connector-python — Oracle's own official MySQL driver for Python, one of the most widely installed database connectors on PyPI — carries no license_expression field. Its live metadata right now:

curl -s https://pypi.org/pypi/mysql-connector-python/json \
  | python3 -c "import json,sys; d=json.load(sys.stdin)['info']; \
    print('license:', d['license']); \
    print('license_expression:', d['license_expression']); \
    print('classifiers:', [c for c in d['classifiers'] if 'License' in c])"
# -> license: GNU GPLv2 (with FOSS License Exception)
# -> license_expression: None
# -> classifiers: ['License :: OSI Approved :: GNU General Public License (GPL)']

The package is GPL-2.0, plain and unambiguous — Oracle spells it out in both the free-text field and the classifier. This is exactly the kind of dependency license-radar exists to catch: a strong-copyleft license pulled into a project's dependency tree.

What license-radar's own resolver does with it

remote.py's reduce_pypi_info() has a documented priority order: license_expression first, then a License :: OSI Approved :: classifier, then the free-text license field. For this package, license_expression is empty, so it correctly falls through to the classifier and extracts the text after the last :::

>>> from license_radar.remote import reduce_pypi_info
>>> info = {
...     "license": "GNU GPLv2 (with FOSS License Exception)",
...     "license_expression": None,
...     "classifiers": ["License :: OSI Approved :: GNU General Public License (GPL)"],
... }
>>> reduce_pypi_info(info)
'GNU General Public License (GPL)'
>>> from license_radar.classify import classify_expression
>>> classify_expression('GNU General Public License (GPL)')
'unknown'

The extraction is correct — that really is the classifier PyPI serves for this package today. The problem is one step later: classify.py's alias table only recognizes compact, SPDX-adjacent spellings ("GPLV3", "GPL V3", "GPL-3.0"). It has no entry for the full official PyPI trove-classifier wording, which is what reduce_pypi_info() actually hands it in practice whenever a package relies on classifiers instead of the newer license_expression field. The same gap holds for every other standard GNU-family classifier, not just this one:

>>> for text in [
...     "GNU General Public License (GPL)",
...     "GNU General Public License v2 (GPLv2)",
...     "GNU General Public License v2 or later (GPLv2+)",
...     "GNU General Public License v3 (GPLv3)",
...     "GNU General Public License v3 or later (GPLv3+)",
...     "GNU Affero General Public License v3",
...     "GNU Affero General Public License v3 or later (AGPLv3+)",
... ]:
...     print(text, "->", classify_expression(text))
GNU General Public License (GPL) -> unknown
GNU General Public License v2 (GPLv2) -> unknown
GNU General Public License v2 or later (GPLv2+) -> unknown
GNU General Public License v3 (GPLv3) -> unknown
GNU General Public License v3 or later (GPLv3+) -> unknown
GNU Affero General Public License v3 -> unknown
GNU Affero General Public License v3 or later (AGPLv3+) -> unknown

Every one of these is real, current PyPI classifier text — not a made-up edge case. A package that predates the license_expression field (most of PyPI's older, established GPL-licensed packages) and never had a compact free-text license alias added has no path in license-radar's resolver to the correct strong-copyleft answer, only to unknown.

A sibling package that gets it right — for a different reason

mysqlclient, a separate, also-widely-used MySQL driver, is correctly recorded in license-radar's own static database:

"mysqlclient": "GPL-2.0-or-later",  # license_expression "GPL-2.0-or-later"

That entry resolves to strong-copyleft — but only because a human copied the exact SPDX id from mysqlclient's (correctly populated) license_expression field into the static DB by hand. It says nothing about whether the classifier-text path itself works; it doesn't, which is exactly what leaves mysql-connector-python — same database engine, same license family, no entry in the static DB, no license_expression on PyPI — with no resolvable answer.

Does this actually let a GPL dependency through?

Not by default. license-radar's default policy treats an unknown tier as a violation (treat_unknown_as_violation: True in policy.py), so a live scan of a project depending on this package still fails and gets a human's attention — just under the wrong label:

$ echo "mysql-connector-python==8.4.0" > requirements.txt
$ python3 -m license_radar.cli scan --online .
[pypi] mysql-connector-python: GNU General Public License (GPL) (unknown) !!

VIOLATIONS FOUND

But treat_unknown_as_violation is a documented, supported policy knob — a team drowning in "unknown" findings from packages with genuinely sparse metadata has a real reason to flip it off rather than allowlist each one by hand. Doing that turns this specific gap from a mislabeled violation into a silent pass, for a package that is unambiguously GPL:

$ echo '{"treat_unknown_as_violation": false}' > policy.json
$ python3 -m license_radar.cli scan --online --policy policy.json .
[pypi] mysql-connector-python: GNU General Public License (GPL) (unknown)

OK — no policy violations

Both commands were run against the real CLI, unmodified, with live --online lookups against the current PyPI API — nothing here is simulated. Full suite, unchanged by this article (no code was modified, only run): 121 passed (pytest tests/ -q, repository root).
