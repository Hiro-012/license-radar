license-radar blog

Notes on the dependency license issues license-radar catches, and why they matter.

license-radar reads four of package.json's five dependency fields

dependencies, devDependencies, optionalDependencies and peerDependencies are all read — bundledDependencies (or bundleDependencies) isn't, so an AGPL-3.0 package declared only there scans as “No dependencies found. OK”.

How a GPL or AGPL dependency becomes a legal problem

Real cases — the BusyBox GPL-enforcement lawsuits and MongoDB's move to SSPL — and how the same risk arrives through an unreviewed transitive dependency.

What license is chardet actually under? It depends which version you pinned

chardet relicensed from LGPL-2.1-or-later to 0BSD partway through its release history — a real case where a license scanner keyed only by package name can't give one correct answer.

OpenJDK is GPL-licensed. So why can you ship it inside closed-source software?

GPL-2.0 WITH Classpath-exception-2.0 — the license clause behind OpenJDK and core Java libraries that lets them link into proprietary code, and why the SPDX “WITH” operator trips up scanners built only for plain GPL.

license-radar says “redis” is MIT. The Redis server hasn't been under one license since 2024

The redis/ioredis client packages are correctly MIT — but the Redis database itself moved from BSD to SSPL/RSALv2 in 2024 and added AGPLv3 in 2025. Why no dependency-manifest scanner can see that gap.

“Unlicense” and “UNLICENSED” look like the same word. license-radar treats them as opposites

Unlicense is a real, OSI-approved, public-domain-equivalent SPDX license. UNLICENSED is npm's own convention for “no rights granted at all.” Even Solidity's own compiler docs have pointed developers at the wrong one.

PyQt5 and PySide6 wrap the same Qt library under different licenses

PyQt5 has no LGPL option — GPLv3 or a paid Riverbank commercial license, full stop. PySide6 ships under LGPLv3 with GPL fallbacks. license-radar's SPDX OR-expression resolver correctly tiers them as strong-copyleft and weak-copyleft, verified against both packages' live PyPI metadata.

tqdm shows up as MIT everywhere. Its own LICENCE file says MPL-2.0 AND MIT

tqdm carries no PyPI license classifier at all and a compound “MPL-2.0 AND MIT” metadata expression — not the plain MIT most sites assume. Why AND isn't a rounding error, and how a scanner that mishandles compound expressions gets it wrong either way.

PyPI lists orjson under three OSI licenses. AND makes sure only one of them actually binds

orjson's classifiers list Apache, MIT and MPL with no structure between them; its real license_expression is the nested “MPL-2.0 AND (Apache-2.0 OR MIT)” — the exact case license-radar's expression resolver cites as its motivating example.

npm's registry says optimist is “MIT/X11”. license-radar's --online scan calls it unknown

A real, currently-published npm package still carries the pre-SPDX slash notation in its own registry metadata. Neither license-radar's free-text alias table nor its SPDX-expression tokenizer resolves it, so the --online fallback path lands on unknown rather than a false permissive verdict.

PyPI's own GPL classifier text says “GNU General Public License” in plain words — license-radar reads it as unknown

mysql-connector-python has no license_expression on PyPI, so license-radar's --online mode falls back to its classifier text. That exact string resolves to unknown instead of strong-copyleft, because the alias table only recognizes compact SPDX-style spellings.

license-radar misses dev-requirements.txt — only the requirements*.txt suffix pattern is scanned

Manifest discovery recognizes a filename only if it starts with “requirements” and ends in “.txt”. dev-requirements.txt and test-requirements.txt — a real, actively-used naming convention — start with the qualifier instead, and are never discovered.

license-radar scans Python and npm manifests. A Go or Conda-only repo gets “OK — no policy violations” too

Manifest discovery matches six exact Python/npm filenames only, as documented. A directory with none of them prints “No dependencies found” then “OK — no policy violations”, exit code 0: indistinguishable from a repo that was actually scanned clean.

license-radar's --online npm lookup only reads the modern “license” field. Pre-2013 packages used “licenses” instead

Packages that predate npm's 2013 license-field migration carry their only license info in the legacy plural “licenses” array, which the lookup never reads. A real MIT package comes back UNKNOWN and trips a policy violation.

license-radar's SPDX parser doesn't implement the “+” operator

spdx_expr.py's tokenizer treats + as an ordinary identifier character, so GPL-2.0+ never becomes the strong-copyleft GPL-2.0-or-later license-radar already recognizes — it becomes an unclassifiable atom that aborts the whole expression, including compound OR expressions.

license-radar reads setup.cfg's install_requires — but not when it points at a file

setuptools' setup.cfg supports install_requires = file: requirements/base.txt to load the dependency list from another file. license-radar recognizes the file: prefix only well enough to skip the line — it never opens the referenced file.

pyproject.toml can say “dependencies live in this other file.” license-radar never opens it

PEP 621 lets a project mark [project] dependencies as dynamic and source them from another file. license-radar reads project.dependencies as a literal list but never resolves the dynamic reference, so a project using this layout scans clean even with a GPL-3.0 package declared.
