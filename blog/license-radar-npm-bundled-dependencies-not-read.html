license-radar reads four of package.json's five dependency fields

By HiroCheck · Published 2026-09-30

npm's package.json has five fields that list a package's dependencies: dependencies, devDependencies, optionalDependencies, peerDependencies, and bundledDependencies (npm also accepts the alternate spelling bundleDependencies). The fifth one exists so a package can ship its own vendored copies of specific dependencies inside its published tarball instead of relying on the installer to fetch them separately — a pattern used by packages that need a pinned, private copy of something at publish time. license-radar's parse_package_json() reads the first four. It has no code path for the fifth, under either spelling.

The function, as implemented

# license_radar/parsers.py:458-471
def parse_package_json(path: Path) -> list[str]:
    data = json.loads(path.read_text())
    names: list[str] = []
    # optionalDependencies are installed when available; peerDependencies are
    # declared as required alongside the package. Both are dependencies the
    # project declares, so both are in scope for a license-compliance scan.
    for section in (
        "dependencies",
        "devDependencies",
        "optionalDependencies",
        "peerDependencies",
    ):
        names.extend(data.get(section, {}).keys())
    return _dedupe(names)

The comment above the loop shows the same reasoning that already justified including optionalDependencies and peerDependencies — both are "dependencies the project declares" and both went into scope. bundledDependencies qualifies under that same reasoning: it is one of npm's five documented package.json dependency fields, and the packages it lists are ordinary registry dependencies that happen to also get bundled into the published tarball, not vendored source with no corresponding registry package. It just isn't in the tuple. There's no filtering logic that excludes it on purpose; the field is simply absent from the list of four.

Reproduced against the unmodified CLI

$ cat package.json
{
  "name": "gap-fixture",
  "version": "1.0.0",
  "bundledDependencies": ["pm2"]
}

$ python3 -m license_radar.cli scan .
No dependencies found.

OK — no policy violations
$ echo $?
0

pm2 is in license-radar's own curated database as AGPL-3.0 — the default policy's own example of a strong-copyleft license. The scan reports the same clean "OK" it would give an empty project.

Control: the identical package, one field over

To confirm the miss is specifically about which field is read — not some other difference in the fixture — the same package name, same version range, declared under dependencies instead, scans exactly as expected:

$ cat package.json
{
  "name": "contrast-fixture",
  "version": "1.0.0",
  "dependencies": {"pm2": "^5.0.0"}
}

$ python3 -m license_radar.cli scan .
[npm] pm2: AGPL-3.0 (strong-copyleft) !!

VIOLATIONS FOUND
$ echo $?
1

Same package, same license, same policy — the only variable is which of package.json's five dependency fields it's declared under. The alternate spelling npm also accepts, bundleDependencies (no "d" after "bundle" — this is not a typo, both spellings are documented and both are honored by npm itself), scans the same way as the first case: still "No dependencies found. OK".

Why this is a different gap from the earlier package.json articles

This blog's earlier npm-legacy-licenses-array-not-read article is about a package.json read incorrectly for its own declared license (the old licenses array field is never consulted). This one is about a project's own package.json — the dependency declaration, not the dependency's own license metadata — having one of its five standard dependency-listing fields skipped entirely by manifest parsing. Neither article's fixture or code path overlaps with the other's.

How this field gets used in practice

bundledDependencies is less common than the other four fields, but it is one of npm's five standard, currently-supported package.json dependency fields, not a deprecated or unofficial one. Packages that vendor a specific, pinned build of a native or platform-specific dependency (so the published tarball is self-contained and installs without a separate registry fetch for that piece) are the field's designed use case. A project relying on it for a copyleft-licensed vendored package gets no warning that the dependency was never inspected at all — the scan output is indistinguishable from a project with zero dependencies.

A project using bundledDependencies for a copyleft package can work around the gap today by also declaring the same package under dependencies or optionalDependencies (both of which license-radar does read) until the field itself is supported.
