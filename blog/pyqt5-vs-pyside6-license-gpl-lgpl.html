PyQt5 and PySide6 wrap the same Qt library under different licenses

By HiroCheck · Published 2026-08-31

Two Python packages give you the same underlying Qt widget toolkit — PyQt5 and PySide6. Swap one for the other in a project and the imports barely change (PyQt5.QtWidgets vs. PySide6.QtWidgets). The license terms you're actually agreeing to do not barely change: one gives you no permissive path at all, the other does. A scanner that treats "it's a GUI binding for Qt" as one fact instead of checking each package's declared license separately will get this wrong.

What each package actually declares

Checked directly against the live PyPI JSON API for both packages:

curl -s https://pypi.org/pypi/PyQt5/json | python3 -c "import json,sys; print(json.load(sys.stdin)['info']['license'])"
> GPL v3

curl -s https://pypi.org/pypi/PySide6/json | python3 -c "import json,sys; print(json.load(sys.stdin)['info']['license'])"
> LGPL-3.0-only OR GPL-2.0-only OR GPL-3.0-only

PyQt5, maintained by Riverbank Computing, is dual-licensed under the GPLv3 and a paid Riverbank Commercial License — and, unlike the Qt library it wraps, PyQt has never offered an LGPL option. If your use case is incompatible with the GPL (closed-source distribution without releasing your own source), the only path is buying a commercial license from Riverbank; there is no free permissive tier to fall back to.

PySide6 — the Qt Company's own official binding, sometimes called "Qt for Python" — is offered under the LGPLv3, with GPLv2/GPLv3 as alternate terms, plus a separate commercial edition from the Qt Company itself. The LGPL option is what makes PySide6 usable in proprietary applications without a commercial license, as long as you dynamically link against Qt rather than statically bundling it.

How license-radar resolves the PySide6 expression

PySide6's declared license isn't a single SPDX id, it's a three-way OR expression. license-radar's SPDX-expression resolver (license_radar/spdx_expr.py) treats an OR as "the licensee may satisfy either side," so the effective obligation is the least restrictive operand — here, LGPL-3.0-only beats both GPL alternatives. Verified against the shipped code:

>>> from license_radar.classify import classify_expression
>>> classify_expression("GPL-3.0-only")
'strong-copyleft'
>>> classify_expression("LGPL-3.0-only OR GPL-2.0-only OR GPL-3.0-only")
'weak-copyleft'

PyQt5's GPL v3 string has no OR to resolve — it's a single strong-copyleft license, full stop, so it lands directly in the strong-copyleft tier without ever reaching the expression parser.

What an actual scan reports

Running the CLI against a requirements.txt listing both packages side by side:

$ cat requirements.txt
pyqt5
pyside6
requests

$ license-radar scan requirements.txt
[pypi] pyqt5: GPL-3.0-only (strong-copyleft) !!
[pypi] pyside6: LGPL-3.0-only (weak-copyleft)
[pypi] requests: Apache-2.0 (permissive)

VIOLATIONS FOUND

Under license-radar's default policy (fail at strong-copyleft or above), pyqt5 trips the scan; pyside6 and requests don't. That's not a coin flip or a name-based guess — it's the direct, mechanical consequence of one package declaring a bare GPLv3 and the other declaring an OR expression with an LGPL branch. pyqt5 is in fact license-radar's own canonical strong-copyleft fixture used across its test suite, precisely because the GPL-only, no-LGPL-option case is real and common enough to be the reference example.

Why "just use PySide instead" isn't a free pass either

The LGPL still carries obligations PyQt5's GPL doesn't even offer a way around: dynamic linking (not static), and giving users the means to relink against a modified version of the LGPL'd library. Static-linking PySide6 into a frozen executable (PyInstaller, Nuitka, a single-file build) can forfeit the LGPL path and pull you back toward the GPL branch of the same OR expression — at which point PySide6 is no more permissive for that build than PyQt5 is. license-radar's weak-copyleft tier is a real compliance obligation, not a "safe" label; it just isn't the strong-copyleft, no-permissive-alternative case that PyQt5 is.

What to actually check

If a project needs Qt bindings and closed-source distribution without a paid license, PySide6's LGPL branch is the one that can work — provided the build actually links dynamically. If it needs to statically bundle Qt, neither package's default terms give a free path, and the real options are a Riverbank commercial license (PyQt) or a Qt Company commercial license (PySide), not a license-radar-detectable technicality. Either way, checking which package a project actually imports — and how it's built, not just what it imports — is the question a dependency-manifest scan can start answering but can't finish on its own.
