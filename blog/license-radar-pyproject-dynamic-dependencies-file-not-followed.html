pyproject.toml can say "dependencies live in this other file." license-radar never opens it

By HiroCheck · Published 2026-09-28

PEP 621 lets a pyproject.toml declare that [project] dependencies is dynamic — computed rather than listed inline — and setuptools' own [tool.setuptools.dynamic] table is the standard way to say where from: dependencies = {file = ["requirements/prod.in"]} tells setuptools (and pip install, and PyPI's own metadata build) to read the real list from that file at build time. It's documented setuptools behavior, not a niche trick, and it exists for the same reason setup.cfg's older install_requires = file: ... directive does: share one requirements file between pip install -r and packaging metadata without duplicating it. license-radar's own README says it reads pyproject.toml. It does — but only the case where dependencies are listed directly in the file, not the case where the file says "look elsewhere."

The function, as implemented

# license_radar/parsers.py
def parse_pyproject_toml(path: Path) -> list[str]:
    data = tomllib.loads(path.read_text())
    names: list[str] = []

    project = data.get("project", {})

    # PEP 621 core dependencies.
    _add_req_strings(names, project.get("dependencies", []))
    ...

project.get("dependencies", []) is exactly correct for the common case — a literal array of PEP 508 strings. But when dynamic = ["dependencies"] is set, PEP 621 requires project.dependencies to be *absent* (a build backend must reject a pyproject.toml that has it both ways). So this line reads an empty list, and nothing anywhere in parse_pyproject_toml() looks at tool.setuptools.dynamic — the table that actually names where the dependencies live. The Poetry, PDM, Hatch and PEP 735 sections that follow it in the same function all read requirements straight out of pyproject.toml itself; none of them, and no other code path in the module, ever opens a file that tool.setuptools.dynamic points at.

Not fixed by independent discovery, either

Even setting the indirection aside, the referenced file would need to be independently discoverable on its own for license-radar to have any chance of seeing it, and the whole point of the file directive is to point at whatever requirements layout a project already uses — requirements/prod.in, requirements/base.txt split from a set of environment overlays, or any other name a team picked before adopting pyproject.toml. Only a file whose name happens to start with requirements and end in .txt is picked up by _matches_manifest()'s requirements*.txt rule; this blog's earlier setup.cfg file: article found the same compounding shape with the same rule. A team that named its shared file requirements/prod.in — a real, common extension for a file that's -r-included rather than installed directly — gets nothing from either code path.

Reproduced against the unmodified CLI

$ cat pyproject.toml
[project]
name = "demo-app"
version = "0.1.0"
dynamic = ["dependencies"]

[tool.setuptools.dynamic]
dependencies = {file = ["requirements/prod.in"]}

[build-system]
requires = ["setuptools"]
build-backend = "setuptools.build_meta"

$ cat requirements/prod.in
PyQt5>=5.15
requests>=2.0

$ python3 -m license_radar.cli scan .
No dependencies found.

OK — no policy violations
$ echo $?
0

PyQt5 is in license-radar's own curated database as GPL-3.0-only — a strong-copyleft license the default policy exists specifically to catch. The scan reports the same clean "OK" it would give an empty project, with no warning that dynamic dependencies exist at all.

Control: the identical file, discoverable

To confirm the miss is specifically about the indirection and the naming pattern — not some other difference — renaming the exact same file to a name discover_manifests() does recognize scans exactly as expected:

$ cp requirements/prod.in requirements/requirements.txt
$ python3 -m license_radar.cli scan .
[pypi] PyQt5: GPL-3.0-only (strong-copyleft) !!
[pypi] requests: Apache-2.0 (permissive)

VIOLATIONS FOUND
$ echo $?
1

Same package, same declared version, same policy — the only variable is whether license-radar's pyproject.toml parsing and manifest-discovery code paths ever see the file the project actually installs from.

Why this is a different gap from the setup.cfg article

The earlier article on this blog (license-radar-setup-cfg-file-directive-dependencies-not-followed.html) covers the same *shape* of bug — a manifest pointing at another file instead of listing dependencies inline — but in setup.cfg, a format parse_setup_cfg() already partially recognizes the file: keyword for (only to skip it). Here the manifest is pyproject.toml, the mechanism is PEP 621's newer dynamic field paired with setuptools' [tool.setuptools.dynamic] table, and parse_pyproject_toml() has no awareness of either — it doesn't even recognize the keyword the way _split_cfg_list() recognizes (and skips) file:. Any project that migrated from setup.cfg to pyproject.toml while keeping a split requirements/ layout — a common migration path, since dynamic exists precisely to ease that transition without inlining dependencies — carries this exact gap forward into the newer format.

A project using this layout can work around the gap today by also keeping a directly-discoverable requirements*.txt at the project root (even a thin one using pip's -r include, which license-radar does follow) until tool.setuptools.dynamic itself is supported.

pip install license-radar
license-radar scan .
