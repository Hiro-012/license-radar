license-radar's --online npm lookup only reads the modern "license" field. Pre-2013 packages used "licenses" instead

By HiroCheck · Published 2026-09-21

Before npm standardized on a single license string (or {type, url} object) in its package.json spec around 2013, the convention was a plural licenses array — [{"type": "MIT", "url": "..."}] — to support dual-licensing. npm's own registry still serves both shapes today: a package published under the old convention and never re-published since carries its license only in that legacy array, with the modern license field simply absent. license-radar's --online lookup reads only the modern field.

The function, as implemented

# license_radar/remote.py
def fetch_npm_license(name: str) -> str | None:
    url = f"https://registry.npmjs.org/{urllib.parse.quote(name, safe='')}"
    try:
        with urllib.request.urlopen(url, timeout=_TIMEOUT) as resp:
            data = json.loads(resp.read())
    except (OSError, ValueError):
        return None

    license_field = data.get("license")
    if isinstance(license_field, str):
        return license_field
    if isinstance(license_field, dict):
        return license_field.get("type")
    return None

There is no branch for data.get("licenses") at all. When a package's registry metadata has no top-level license key — true for anything published and never touched since before the convention changed — the function falls straight through every isinstance check to return None, indistinguishable from a genuinely unlicensed package or a network failure.

A real package that still hits this

node-uuid is the predecessor to today's uuid package — deprecated in favor of it years ago, but still resolvable by name and still present as a pinned or transitive dependency in older lockfiles. Its registry entry was never migrated to the modern field:

$ python3 -c "
import urllib.request, json
with urllib.request.urlopen('https://registry.npmjs.org/node-uuid') as r:
    data = json.loads(r.read())
latest = data['dist-tags']['latest']
v = data['versions'][latest]
print('top-level license:', data.get('license'))
print('latest version:', latest)
print('version-level license:', v.get('license'))
print('version-level licenses:', v.get('licenses'))
"
top-level license: None
latest version: 1.4.8
version-level license: None
version-level licenses: [{'type': 'MIT', 'url': 'https://raw.github.com/broofa/node-uuid/master/LICENSE.md'}]

The registry knows this package is MIT-licensed — it just says so in the field fetch_npm_license() doesn't check.

Reproduced against the unmodified CLI

A minimal package.json depending on it, scanned with --online against the live registry (no local DB entry for node-uuid, so the online lookup is the only source of license data):

$ cat package.json
{
  "name": "repro-verify",
  "version": "1.0.0",
  "dependencies": {
    "node-uuid": "^1.4.8"
  }
}

$ python3 -m license_radar.cli scan . --online --json
{
  "findings": [
    {
      "ecosystem": "npm",
      "package": "node-uuid",
      "license": "UNKNOWN",
      "tier": "unknown",
      "violation": true
    }
  ],
  "violation": true
}
$ echo $?
1

An MIT-licensed dependency — permissive, no compliance concern at all — comes back as unknown and trips treat_unknown_as_violation, the same default-policy gate covered by this blog's earlier piece on GPL trove-classifier text (gpl-trove-classifier-text-reads-as-unknown.html). There the value was fetched but not recognized by the classifier; here nothing is fetched at all, because the field the code looks for doesn't exist in this package's metadata.

Why this is a different gap from the "MIT/X11" article

An earlier article on this blog (optimist-mit-x11-license-online-lookup-unknown.html) covers a related-sounding but distinct failure: there, fetch_npm_license() successfully extracts a string ("MIT/X11") from the modern license field, and it's classify_license() downstream that fails to recognize that string's format. Here, the modern field is absent entirely — fetch_npm_license() returns None before classify_license() is ever called, because the only license data the registry actually has for this package is in a field the function was never written to look at. The fix location is different too: adding an alias entry to the classifier's lookup table would do nothing for this case, since no string ever reaches it.

How common this still is

node-uuid is not a hypothetical edge case — it has over a decade of published versions and remains resolvable and installable today, and projects that pinned it before migrating to uuid can still carry it as a transitive dependency. The npm registry does not retroactively rewrite old packages' metadata to the modern field when the spec changes; a package's package.json at publish time is what the registry serves back, unchanged, for as long as that version stays published. Any pre-2013 package whose most recent version was never re-published is a candidate for this same gap.

A project that depends on packages this old can work around the gap today by pinning a known-correct license for them explicitly in its own override list, if license-radar's policy configuration supports one, rather than relying on --online to resolve them automatically.
