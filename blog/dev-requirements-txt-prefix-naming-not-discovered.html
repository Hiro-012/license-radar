license-radar misses dev-requirements.txt — only the requirements*.txt suffix pattern is scanned

By HiroCheck · Published 2026-09-16

license-radar's manifest discovery recognizes a pip requirements file by one rule: the filename must start with requirements and end with .txt. That covers requirements.txt and requirements-dev.txt fine. It does not cover the equally common naming convention where the qualifier comes first — dev-requirements.txt, test-requirements.txt — and those files are skipped entirely, with no warning.

The matching rule, as implemented

# license_radar/parsers.py
def _matches_manifest(name: str) -> tuple[str, object] | None:
    ...
    if name.startswith("requirements") and name.endswith(".txt"):
        return "pypi", parse_requirements_txt
    return None

Checked directly against both naming conventions:

>>> from license_radar.parsers import _matches_manifest
>>> _matches_manifest("requirements-dev.txt")
('pypi', <function parse_requirements_txt at 0x...>)
>>> _matches_manifest("dev-requirements.txt")
None
>>> _matches_manifest("test-requirements.txt")
None

Reproduced with a real violation

A project with a normal-looking dependency split — runtime deps in requirements.txt, dev/test tooling in dev-requirements.txt — where the dev file happens to pull in a GPL-3.0 package (a common way this actually happens: a test harness or internal tool depends on a GPL-licensed library, and nobody treats a "dev-only" dependency as a license question):

$ cat requirements.txt
requests==2.31.0
flask==3.0.0

$ cat dev-requirements.txt
pyqt5==5.15.9
pytest==7.4.0

$ license-radar scan .
[pypi] requests: Apache-2.0 (permissive)
[pypi] flask: BSD-3-Clause (permissive)

OK — no policy violations

pyqt5 (GPL-3.0-only, license-radar's own database entry) is never scanned — the file it lives in was never discovered, so it never even reaches the classification step. Renaming the exact same file to the suffix-style convention the matcher does recognize changes the outcome completely, with no other change to its contents:

$ mv dev-requirements.txt requirements-dev.txt
$ license-radar scan .
[pypi] pyqt5: GPL-3.0-only (strong-copyleft) !!
[pypi] pytest: MIT (permissive)
[pypi] requests: Apache-2.0 (permissive)
[pypi] flask: BSD-3-Clause (permissive)

VIOLATIONS FOUND

Same dependency, same license, same default policy (treat_unknown_as_violation doesn't even come into play here — pyqt5 classifies cleanly to strong-copyleft). The only variable is which side of the word "requirements" the qualifier sits on.

This isn't a rare naming choice

There's no PEP or pip specification for how to name a secondary requirements file — the convention is purely community habit, and the community didn't converge on one order. Real, currently-maintained projects use the prefix form directly: zhmcclient's dev-requirements.txt is a working example, not a hypothetical one. Searches on the convention consistently turn up both orderings in active use with no indication either has become standard — which means a scanner that only recognizes one of the two orderings will have a real, non-trivial false-negative rate across the ecosystem it claims to cover, not just a theoretical edge case.

What this does and doesn't affect

The three other supported pip manifest formats — pyproject.toml, setup.py, setup.cfg — match on exact, fixed filenames with no prefix/suffix ambiguity, so this gap is specific to the free-form requirements*.txt naming space. Pipfile and package.json are likewise exact-name matches and unaffected. A project that declares all of its dependencies — including dev/test tooling — in pyproject.toml's [dependency-groups] or [tool.poetry.group.*.dependencies] (both already handled, see license-radar's earlier coverage of Poetry and PEP 735 dependency groups) sidesteps this entirely; the gap only bites projects that still split dependencies across loosely-named .txt files, which is most of the pip ecosystem that predates pyproject.toml becoming common.

Verification

$ python3 -m pytest license_radar/../tests -q
121 passed

No code change was made in this session — the gap is a discovery-content finding, not a fix, and the existing test suite (121 passed) reflects that: none of the fixtures exercise a prefix-style requirements filename, so this session's finding doesn't move that number. Note that pointing the CLI directly at the file does not work around this — the same filename gate applies whether the scan target is a directory or a single path:

$ license-radar scan dev-requirements.txt
No dependencies found.

OK — no policy violations

The only reliable workaround today is to rename the file to a recognized requirements*.txt pattern (e.g. requirements-dev.txt) before scanning, or to call the parser function directly from Python, bypassing filename matching entirely:

>>> from pathlib import Path
>>> from license_radar.parsers import parse_requirements_txt
>>> from license_radar import license_db, classify
>>> names = parse_requirements_txt(Path("dev-requirements.txt"))
>>> [(n, classify.classify_expression(license_db.lookup("pypi", n))) for n in names]
[('pyqt5', 'strong-copyleft'), ('pytest', 'permissive')]
pip install license-radar
license-radar scan requirements-dev.txt
