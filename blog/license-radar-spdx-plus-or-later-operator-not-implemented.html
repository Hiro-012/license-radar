license-radar's SPDX parser doesn't implement the "+" operator — GPL-2.0+ reads as unknown, and it takes X OR Y down with it

By HiroCheck · Published 2026-09-23

The SPDX License List has always permitted a trailing + on a GPL-family identifier to mean "this version or any later version" — it predates the now-preferred -or-later suffix and is still valid, spec-legal syntax, still emitted by real package metadata today. license-radar already recognizes GPL-2.0-or-later as strong-copyleft. It does not recognize GPL-2.0+ — the older spelling of the exact same license.

Where it breaks

# license_radar/spdx_expr.py, _tokenize_spdx()
j = i
while j < n and (expr[j].isalnum() or expr[j] in ".-+_"):
    j += 1
...
word = expr[i:j]
...
tokens.append(("ID", word))

+ is listed as an ordinary identifier character, right alongside . and -. So the atom GPL-2.0+ tokenizes as a single opaque identifier, ("ID", "GPL-2.0+") — not as the id GPL-2.0 followed by a distinct "or-later" operator. That token then reaches classify.py:

# license_radar/classify.py
STRONG_COPYLEFT = {
    "GPL-2.0-only", "GPL-2.0-or-later", "GPL-3.0-only", "GPL-3.0-or-later",
    "AGPL-3.0-only", "AGPL-3.0-or-later", "SSPL-1.0",
}
...
def classify_license(spdx: str | None) -> str:
    if not spdx:
        return TIER_UNKNOWN
    normalized = _normalize(spdx)
    if normalized in PERMISSIVE: return TIER_PERMISSIVE
    if normalized in WEAK_COPYLEFT: return TIER_WEAK_COPYLEFT
    if normalized in STRONG_COPYLEFT: return TIER_STRONG_COPYLEFT
    return TIER_UNKNOWN

"GPL-2.0+" is in neither the tier sets nor the _ALIASES table (which maps bare forms like "GPL-2.0" to "GPL-2.0-only", but has no entry for the +-suffixed spelling). It falls through every branch and comes back unknown — the same tier as a license the tool has genuinely never heard of, not the strong-copyleft tier it actually is.

It also takes compound expressions down with it

spdx_expr.py's own module docstring describes its design explicitly: "any atom we cannot classify … makes the whole expression TIER_UNKNOWN — the resolver refuses to guess rather than let a min()/max() silently swallow an unclassifiable branch." That's the right call for a genuinely unrecognized license — but GPL-2.0+ isn't one, and the refusal applies anyway:

$ python3 -c "
from license_radar.classify import classify_expression
print(classify_expression('GPL-2.0+'))
print(classify_expression('GPL-2.0+ OR MIT'))
print(classify_expression('GPL-2.0-or-later OR MIT'))
print(classify_expression('GPL-2.0-or-later'))
"
unknown
unknown
permissive
strong-copyleft

GPL-2.0+ OR MIT should resolve to permissive — the licensee may pick MIT, exactly as GPL-2.0-or-later OR MIT correctly does one line below it. Because _parse_atom() raises on the single unrecognized GPL-2.0+ token, the whole OR expression aborts before the parser ever gets to weigh the MIT branch.

A real package carrying exactly this string today

python-vlc — the official Python bindings for the VLC media player — declares its license in PyPI metadata, right now, as the literal string "LGPL-2.1+":

$ curl -s https://pypi.org/pypi/python-vlc/json \
  | python3 -c "import json,sys; d=json.load(sys.stdin)['info']; \
    print('license:', d['license']); \
    print('license_expression:', d['license_expression'])"
license: LGPL-2.1+
license_expression: None

This is not a contrived string — it's the exact convention this article describes, sitting in a live, currently-published, widely-used package's metadata. (This particular package also carries an OSI-Approved classifier, and reduce_pypi_info() prefers that classifier text over the free-text license field when both are present — a different, already-covered gap on this blog, see gpl-trove-classifier-text-reads-as-unknown.html. The +-operator gap described here is independent of that priority order: it fires on whatever string ultimately reaches classify_expression(), regardless of which field it came from — and for --online npm lookups specifically, fetch_npm_license() has no classifier fallback at all, so an npm package's raw license field goes straight through unfiltered.)

Reproduced end to end against the unmodified CLI

A minimal requirements.txt naming one dependency, with a license lookup returning "GPL-2.0+" for it (standing in for what an npm registry response or a local DB entry could just as easily supply verbatim — license_radar.cli and license_radar.classify run completely unmodified in both cases below):

$ cat requirements.txt
old-gpl-pkg==1.0

$ python3 -m license_radar.cli scan requirements.txt
[pypi] old-gpl-pkg: GPL-2.0+ (unknown) !!

VIOLATIONS FOUND
$ echo $?
1

Flagged — but for the wrong reason (unknown, not strong-copyleft), and that distinction matters the moment a project uses a policy that treats them differently. The default policy's treat_unknown_as_violation knob is exactly such a case, documented in policy.py and legitimately used by teams that want unrecognized-but-plausibly-fine licenses to warn rather than block a build:

$ cat policy.json
{"treat_unknown_as_violation": false}

$ python3 -m license_radar.cli scan requirements.txt --policy policy.json
[pypi] old-gpl-pkg: GPL-2.0+ (unknown)

OK — no policy violations
$ echo $?
0

$ # control: same dependency, "-or-later" spelling, same lenient policy
$ python3 -m license_radar.cli scan requirements.txt --policy policy.json
[pypi] old-gpl-pkg: GPL-2.0-or-later (strong-copyleft) !!

VIOLATIONS FOUND
$ echo $?
1

Same dependency, same actual license, same policy file. The only difference is which of the two spec-legal spellings the upstream metadata happens to use. One is caught as strong-copyleft; the other passes clean.

Why this is a different gap from the other GPL-related articles

Three earlier posts on this blog also involve GPL/LGPL strings landing in unknown: gpl-trove-classifier-text-reads-as-unknown.html is about free-text PyPI classifier sentences ("GNU General Public License v2 or later (GPLv2+)") missing from the alias table — English prose, handled entirely inside classify_license()'s alias lookup. license-radar-npm-legacy-licenses-array-not-read.html is about a field npm's fetch function never reads at all — the string never even reaches the classifier. pyqt5-vs-pyside6-license-gpl-lgpl.html and orjson-mpl-and-apache-or-mit-license-expression.html exercise the OR/AND reduction logic itself, but only with atoms already in the recognized set. This gap is different from all four: it's a compact, spec-legal SPDX expression token — exactly the kind of string spdx_expr.py's own docstring claims to implement "SPDX operator semantics" for — failing inside the tokenizer of that same module, because one of the grammar's own operators was never given a code path. No alias-table entry could fix it, because the failure happens before classify_license()'s alias lookup is even the relevant question: the tokenizer hands over a single fused token, "GPL-2.0+", with no way for anything downstream to tell "known id" and "operator suffix" apart.

A project depending on a package whose upstream metadata uses the + spelling can work around this today by overriding that specific dependency's license in its own local DB entry, if license-radar's configuration supports one, rather than relying on the automatic classifier to normalize it.

pip install license-radar
license-radar scan .
