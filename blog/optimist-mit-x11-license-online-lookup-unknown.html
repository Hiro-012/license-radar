npm's registry says optimist is "MIT/X11". license-radar's --online scan calls it unknown

By HiroCheck · Published 2026-09-12

optimist — the argument-parsing library that predates and inspired yargs, still published and still installable as a transitive dependency of older tooling — carries a license string in npm's own registry metadata that predates npm's move to plain SPDX identifiers:

curl -s https://registry.npmjs.org/optimist | python3 -c \
  "import json,sys; d=json.load(sys.stdin); \
   v=d['versions'][d['dist-tags']['latest']]; \
   print(v['license'])"
# -> MIT/X11

That is the actual, current value in the live registry for optimist's latest published version (0.6.1) — not a synthetic test fixture. It comes from an era before npm standardized the license field on a single SPDX identifier: an older convention wrote the license as two names joined by a slash, on the understanding that they name the same permissive terms under two different historical labels.

What license-radar does with it

license-radar's static package database doesn't carry an entry for optimist, so a --online scan is the only way it learns optimist's license at all — it falls through to a live registry lookup (license_radar/remote.py) exactly as designed. Feeding the registry's own answer back through license-radar's classifier reproduces the gap directly, end to end, no mocking:

>>> from license_radar.remote import fetch_npm_license
>>> from license_radar.scanner import scan_manifest
>>> fetch_npm_license("optimist")
'MIT/X11'
>>> scan_manifest(Path("package.json"), online=True)   # deps: {"optimist": "^0.6.1"}
[Finding(ecosystem='npm', package='optimist', license='MIT/X11', tier='unknown')]

Two independent paths inside classify.py both decline to resolve the string, and both do it for defensible reasons rather than by accident:

>>> from license_radar.classify import classify_license, classify_expression
>>> classify_license("MIT/X11")
'unknown'      # not in PERMISSIVE, not in the free-text _ALIASES map either
>>> classify_expression("MIT/X11")
'unknown'      # falls back to the SPDX-expression parser, which also fails

The free-text alias table only has an exact-match entry for "MIT LICENSE", not the slash form. And the SPDX-expression resolver's tokenizer (spdx_expr.py) treats / as a character outside the SPDX-expression grammar — the same rule that makes any stray punctuation abort the whole expression rather than let the parser guess at a partial match — so "MIT/X11" is rejected as a tokenization failure before either half of it is even inspected as a license id.

Why this isn't a false permissive verdict

Nothing here lets a copyleft obligation slip through unflagged. Both code paths refuse to guess and land on unknown — the same conservative outcome the SPDX expression resolver already documents for any unrecognized atom (see the earlier post on the WITH operator, which fails the same direction on purpose). The practical cost is precision, not safety: a policy that treats unknown as requiring manual review (license-radar's own default policy does exactly this) will flag optimist for a human to look at, even though the package is, by every account other than this one slash character, an ordinary permissive dependency. At scan-report scale, that's exactly the kind of package a reviewer learns to skim past — which is the actual cost of a spurious "unknown": not a wrong verdict, but noise that erodes trust in the verdicts that matter.

Scope of this finding

This is specific to the --online remote-lookup fallback, which only activates for a dependency absent from license-radar's curated static DB. The default (offline) scan path — DB lookup only, no network call — never reaches fetch_npm_license and is entirely unaffected. No code was changed for this post, and none of the accuracy corpus concerns optimist or the --online path, so the existing measured numbers are unchanged: full suite 121 passed (pytest -q, repository root, including the newly-verified test_packaging.py invariants), and the default-policy accuracy harness reports recall 100% (13/13 known-risky packages caught) and false-positive rate 0% (0/292 non-risky packages) (scripts/measure_accuracy.py, run directly against the current 305-package curated DB).
