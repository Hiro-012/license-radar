What license is chardet actually under? It depends which version you pinned

By HiroCheck · Published 2026-08-07

chardet (the character-encoding detector many Python projects pull in transitively through requests or similar HTTP libraries) changed its license partway through its release history:

Version rangeLicense
≤ 5.2.0LGPL-2.1-or-later (weak-copyleft — modifications to chardet itself must be shared under LGPL, but merely linking/importing it usually doesn't obligate your own code)
6.x / 7.x0BSD (permissive — effectively public-domain-equivalent, no conditions)

Checked directly against the live PyPI JSON API: chardet 5.2.0 reports the classifier LGPLv2+, while chardet 7.4.3 reports the license expression 0BSD. Same package name, two materially different licenses depending on which release is actually pinned.

Why this breaks a lot of license scanners

Most lightweight license-compliance tools work off an offline table keyed by package name: "package X → license Y." That's fast and doesn't need a network call, but it silently assumes a package's license is a fixed fact about the package rather than a fact about a specific version of it. For a package that relicensed mid-history, a name-keyed table has to pick one answer — and whichever one it picks is wrong for the other half of that package's users.

This isn't a hypothetical edge case — it's a real, checkable relicense:

curl -s https://pypi.org/pypi/chardet/5.2.0/json | grep -i classifier
curl -s https://pypi.org/pypi/chardet/7.4.3/json | grep -i license_expression

What to do about it

If a project depends on chardet, the LGPL-vs-permissive question isn't "what license is chardet," it's "what version of chardet is actually pinned." Check the lockfile, not the package's PyPI landing-page tagline (which, like many older packages, may not reflect the relicense). On 5.2.0 or earlier in a closed-source product, LGPL's terms around modification and linking are worth reading rather than assuming "it's just a dependency."

How license-radar handles this

license-radar scans Python and Node dependency manifests for copyleft license risk. Its offline database deliberately omits packages like chardet whose license isn't stable across versions — rather than guessing, it reports them as unknown and flags them for manual review. Pass --online to query live PyPI/npm metadata for the exact pinned version instead of relying on a name-only offline table:

pip install license-radar
license-radar scan . --online

license-radar also resolves compound SPDX expressions like A OR B and A AND B by their actual operator semantics instead of reporting them as unknown outright — but a package whose license genuinely changed across its history, like chardet, is a different problem that only a version-aware, ideally online, check can answer correctly.
